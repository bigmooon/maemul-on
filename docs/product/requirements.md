## 1. 제품의 중심과 확정 사항

공인중개사가 자신의 매물 Excel을 등록하고, **앞으로 달력 기준 3개월 내 계약 만기 매물을 먼저 확인하여 고객에게 연락하고 상담 결과를 기록하는 웹앱**이다. 내 매물은 주요 관리 아파트와 기타로 나누어 관리하며, 조건 검색과 별도 챗봇을 제공한다. 네이버 로그인과 네이버 캘린더 API를 지원한다.

### 최신 사용자 정정 — 확정 요구

1. 네이버 계정으로 로그인할 수 있어야 한다.
2. 네이버 캘린더 API를 연동하여 업무 일정 관리를 도와야 한다. 캘린더 연동을 일괄 후순위로 두었던 기존 명세를 정정한다.
3. 제품의 매물 분리는 사무소별 분리가 아니라 **주요 관리용 아파트 / 기타**다. 사무소 생성·선택·직원 초대와 사무소 테넌트 기능은 MVP 요구사항에서 제거한다.

AI·RAG·OCR/VLM·Agent는 업무를 돕는 수단이다. 만기 확인 → 고객 연락 → 상담 기록의 중심을 변경하지 않는다. 챗봇은 필수지만, 챗봇 없이도 핵심 업무를 완료할 수 있어야 한다.

### 아직 확정되지 않은 세부안

- 주요 관리 아파트를 지정하는 방식, 여러 아파트 지정 여부와 초기 분류 UI는 아래의 최소 설계안으로 검증한다.
- 네이버 캘린더의 최소 연동안은 사용자가 선택한 업무 일정의 등록이다. 전체 조회·삭제·양방향 동기화까지 확정된 요구나 지원 기능으로 취급하지 않는다.
- 다른 계정과 공동 관리하는 기능은 요청되지 않았다. MVP는 개인 로그인 계정의 내 자료 관리로 설계한다. 공동 관리가 필요하면 별도 권한 설계를 협의한다.

## 2. 사용자와 제품 검증 원칙

핵심 업무 사용자 유형은 **Excel로 임대 매물을 관리하고, 만기 후속 연락 시 고객 정보와 지난 상담을 확인해야 하는 공인중개사**다.

초기 실사용자는 어머니이며, 40대 이상 여성 공인중개사의 사용성을 우선 관찰한다. 연령·성별만으로 숙련도나 디자인 취향을 단정하지 않는다. 큰 글씨·버튼, 적은 선택지, 쉬운 용어, 상세의 점진적 노출은 실제 과제로 검증한다.

다음은 현재 제품 가설이며 검증된 효과가 아니다.

- 기존 Excel보다 만기·연락 업무를 쉽게 완료한다.
- 등록 이후 상담·계약 정보를 웹앱에서 계속 갱신한다.
- 전문 서비스로 전면 전환하는 것보다 초기 도입 부담이 낮다.
- 일부 상담 검색에서 자연어·의미 검색이 더 유용하다.

한 명의 피드백이나 호의적인 의견을 시장 전체의 수요로 표현하지 않는다.

## 3. 매물 분류와 접근 권한 — 다른 개념

### 3.1 주요 관리 아파트 / 기타

사용자의 관리 분류다. 권한 경계나 별도의 DB를 뜻하지 않는다.

최소 설계안:

- 사용자가 주로 관리하는 아파트를 지정하고, 해당 아파트에 연결된 매물을 ‘주요 관리 아파트’에서 확인한다.
- 지정한 주요 관리 아파트에 속하지 않는 내 매물은 ‘기타’에서 확인한다. 기타는 비아파트 매물만을 뜻하지 않는다.
- 내 매물 화면에서 ‘전체 / 주요 관리 아파트 / 기타’를 간단히 선택할 수 있다.
- 주요 관리 아파트가 여러 곳이면 해당 분류 안에서 아파트를 선택할 수 있게 하되, 여러 단계의 복잡한 메뉴는 만들지 않는다.
- 분류 변경은 매물·계약·고객·상담 이력을 삭제하거나 복제하지 않는다.
- 아파트 별칭과 동일 이름의 다른 단지를 주의한다. 불확실한 연결은 자동 확정하지 않고 사용자 확인을 받는다.
- 초기 지정 방식과 Excel 재업로드 시 분류 유지 방법은 실제 양식으로 검증한다.

홈의 기본 만기 목록은 **주요와 기타를 포함한 내 매물 전체**를 대상으로 한다. 주요 분류만 기본 조회하여 기타의 만기를 숨기지 않는다. 이 기본값 변경은 별도 사용자 확인이 필요하다.

### 3.2 로그인 사용자별 개인정보 보호

사무소별 테넌트 요구를 제거해도 다른 로그인 사용자의 자료를 노출하지 않는다.

- MVP 자료 소유·접근 범위는 로그인 사용자 기준이다.
- API·DB·파일·검색·인용·대화·캐시·캘린더 호출에서 서버가 로그인 사용자 권한을 검증한다.
- 클라이언트나 LLM이 보낸 사용자 ID만 신뢰하지 않는다.
- 주요/기타 분류 조건은 사용자의 허가된 자료 범위 안에서만 적용한다.
- 같은 아파트를 관리한다는 이유로 다른 계정의 매물·고객 자료를 공유하지 않는다.
- 사무소 테이블·사무소 ID를 필수 원장이나 검색 필터로 요구하지 않는다.

## 4. 화면과 사용자 여정

### 4.1 로그인

- 네이버 로그인 버튼으로 가입·재로그인을 제공한다. 별도 비밀번호 생성을 강제하지 않는다.
- 최초 로그인 후 엑셀 미등록 안내, 이후에는 홈을 연다.
- 로그인 취소·실패는 쉬운 문구와 재시도 경로를 제공한다.
- 로그아웃은 매물온 세션을 종료한다. 네이버 계정 자체의 로그아웃과 혼동하지 않는다.
- 캘린더 이용 실패나 권한 문제로 내 매물 조회·상담 저장을 막지 않는다.

### 4.2 기본 메뉴: 홈 / 내 매물 / 챗봇

고객·캘린더·Excel을 각각 독립 대시보드로 늘리지 않는다. 고객과 일정 등록은 매물 상세에서 제공하고, 계정·연동 상태는 작은 계정 영역에서 확인하는 설계안을 우선한다.

### 4.3 홈: 중앙의 만료 임박 매물

- 별도 홍보 히어로 대신 중앙에 ‘만료 임박 매물 N건’을 표시한다.
- 오늘부터 달력 기준 3개월 뒤까지 양 끝 포함, 가까운 날짜 순으로 최대 3건을 우선 보여준다. 제목은 전체 대상 건수다.
- ‘모두 보기’는 동일한 만기 범위의 전체 목록을 연다. 주요/기타 모두 포함한다.
- 카드: 매물명·동/호수, 만기일·남은 일수, 고객·역할, 연락 상태, ‘연락·메모’ 버튼.
- 금액·연락처·특이사항·이전 상담·일정 등록은 상세에 둔다.
- 연락 기록이 있어도 만기 목록에 남는다. 날짜 경과만으로 계약을 자동 종료하거나 삭제하지 않는다.
- 날짜 누락은 기간 목록에 섞지 않되 ‘만기일 확인 필요’로 접근할 수 있게 한다. 작은 안내의 위치는 사용성 검증으로 결정한다.
- 예상 날짜는 ‘예상·확인 필요’로 표시한다. 확정값처럼 답하지 않는다.
- 홈에는 챗봇 입력창·복잡한 통계·원본 셀 근거·전체 캘린더를 붙이지 않는다.

날짜 규칙: Asia/Seoul 기준 오늘을 사용하고 계약일은 날짜형으로 저장한다. 고정 90일이 아니다. 월말은 대상 월 말일로 보정한다. 예: 2026-01-31 + 3개월 = 2026-04-30. 실제 종료 처리된 계약은 기본 목록에서 제외하되 이력은 보존한다.

### 4.4 내 매물: 분류·검색·등록

- 전체 / 주요 관리 아파트 / 기타 분류를 제공한다.
- 매물명·동/호수, 거래 유형, 만기 조건을 기본으로 제공한다. 추가 조건은 필요할 때 펼친다.
- 상단 ‘엑셀 올리기’ → 필요한 값 확인·수정 → 등록. 정상 항목까지 반복 확인시키지 않는다.
- 지원 양식을 명시한다. ‘모든 Excel 완벽 지원’이라고 표현하지 않는다.
- 주요 관리 아파트 지정·분류 확인은 별도 대형 설정 화면보다 등록·내 매물 흐름 안에서 제공하는 방안을 검증한다.

### 4.5 매물 상세: 고객·상담·계약 갱신·일정 등록

- 선택한 매물 상세로 이동하고, 돌아가면 이전 화면의 분류·검색 조건을 유지한다.
- 매물·계약 요약, 고객명·역할·연락처, 상담 입력과 연락 결과 저장을 먼저 보여준다. 이전 기록은 펼친다.
- ‘연락 기록’은 실제로 한 연락의 기록이다. 문자·통화를 발송하지 않는다.
- 연락 시도와 업무 해결을 같은 의미로 취급하지 않는다. 최소 상태 표현은 실제 업무 관찰로 확정한다.
- 만기·금액 등 수정은 명시적으로 저장하며 이전 값과 상담 이력을 보존한다.
- ‘네이버 캘린더에 등록’으로 필요한 일정만 선택해 확인 후 등록한다.

### 4.6 챗봇: 독립 읽기·검색 화면

- 질문 입력과 예시 2~3개. 홈에 입력창을 붙이지 않는다.
- 예: ‘주요 관리 아파트 중 3개월 내 만기인 전세’, ‘기타 매물 중 아직 연락 안 한 고객’, ‘반려동물 이야기를 나눴던 월세’.
- 정형 질문은 검증된 DB 조건 조회, 비정형 질문은 상담·특이사항 근거 검색으로 처리한다.
- 짧은 답변과 상세로 이동 가능한 매물 목록을 우선한다.
- 상담 해석에는 상담일·짧은 해당 기록을 제공한다. 만기일에 Excel 파일명·시트·셀 위치를 붙이지 않는다.
- 근거가 없으면 ‘관련 기록에서 확인할 수 없어요’라고 답한다. 검색 실패를 매물 부재로 단정하지 않는다.
- MVP는 읽기 전용이다. 데이터 수정과 캘린더 등록을 모델이 확인 없이 실행하지 않는다.

## 5. 기능 요구사항과 완료 조건

| ID | 기능 | 우선순위 | 완료 조건 |
|---|---|---|---|
| F01 | 네이버 로그인 | 필수 | 승인된 흐름으로 사용자 식별·세션 발급·재로그인·취소/실패 처리가 동작한다. 등록·검수 조건을 확인한다. |
| F02 | 내 자료 접근 보호 | 필수 | 다른 사용자 자료의 API·파일·검색·인용·캘린더 접근을 차단한다. 사무소 테넌트 생성은 요구하지 않는다. |
| F03 | Excel 등록·확인 | 필수 | 지원 .xls/.xlsx 양식에서 변환안을 만들고 중요 값의 누락·불확실성을 수정한 뒤 확정 등록한다. 재시도는 중복 저장하지 않는다. |
| F04 | 주요 관리 아파트 / 기타 분류 | 필수 | 허가된 내 매물을 분류 조회·변경할 수 있고 이력이 유지된다. 동일 단지명 오연결을 확인한다. |
| F05 | 3개월 내 만기 홈 | 필수 | 날짜 경계·정렬·전체 건수·3건 우선 표시·모두 보기·예상/누락/경과가 올바르다. 기타도 포함한다. |
| F06 | 고객 연락·상담 | 필수 | 계약·고객 역할별로 기록하고 재접속 후 유지한다. 이름만으로 병합하거나 다른 계약의 상태를 바꾸지 않는다. |
| F07 | 계약 수동 갱신·이력 | 필수 | 새 날짜·금액을 확인 저장하고 이전 값·상담을 보존한다. 홈과 검색은 새 값으로 조회한다. |
| F08 | 조건 검색·별도 챗봇 | 필수 | 주요/기타를 포함한 검증된 조건으로 실제 내 데이터를 조회하고 상세로 연결한다. 임의 SQL은 실행하지 않는다. |
| F09 | 상담 근거 검색 | 필수 기본 검색 / 의미 검색은 검증 후 | keyword/FTS로 관련 기록을 찾고 근거를 연결한다. RAG를 추가하면 동일 질문으로 검색·인용·거절 성능을 비교한다. |
| F10 | 네이버 캘린더 API 등록 | 필수·외부 연동 검증 필요 | 사용자가 확인한 일정이 본인 캘린더에 등록되고 결과가 기록된다. 취소·권한 오류·중복 클릭·응답 불명 상태를 처리한다. |
| F11 | 삭제·실패 복구·관측 | 필수 | 원본·파생 데이터 삭제 범위, 저장 결과·재시도, 개인정보 없는 오류·지연·비용 기록을 제공한다. |
| F12 | 기존 캘린더 일정 수정 | 기술 검증 후 범위 확정 | API 실제 동작과 일정 식별자를 검증하기 전 자동 수정 완료를 약속하지 않는다. 기존 등록 일정과 변경된 계약의 차이를 안내한다. |

## 6. 등록 이후 데이터 갱신과 캘린더 경계

### 6.1 Excel과 업무 DB

최소 설계안은 **Excel은 최초 가져오기 출발점, 등록한 매물의 계약·상담 최신값은 웹앱 DB**다. 이는 사용자 수용 여부를 검증해야 하는 설계 가정이다.

- 계약 변경은 상세에서 저장하고 홈·검색에 반영한다.
- 동일 파일을 재업로드했다고 기존 계약·상담을 자동 덮어쓰지 않는다.
- 중복 후보와 갱신 계약은 구분한다. 중요 값 충돌은 확인 전 확정 반영하지 않는다.
- 자동 양방향 Excel 동기화는 MVP에서 하지 않는다.
- 사용자가 Excel과 웹앱에 계속 이중 입력해야 한다면 제품 가정을 재검토한다.

### 6.2 네이버 캘린더 최소 연동안

사용자 요구는 ‘네이버 캘린더 API 연동’이다. 아래는 이를 작게 구현하기 위한 제안이며 일정 종류·기본값은 사용자 검증 후 확정한다.

1. 상세에서 계약 만기 일정 또는 후속 연락 일정 등록을 선택한다.
2. 날짜·필요 시 시간을 확인한다. 누락·예상 날짜를 확정 일정으로 몰래 등록하지 않는다.
3. 캘린더로 전송할 제목·설명 미리보기를 확인하고 등록한다.
4. 서버가 본인 권한을 검증해 API를 호출하고 성공/실패를 표시한다.

- 고객명·전화번호·상담 본문은 기본 전송하지 않는다. 제목은 ‘매물온 일정’과 최소 식별 정보로 시작하는 안을 검증한다. 상세 링크를 넣더라도 로그인 권한을 유지한다.
- 계약 DB가 최신 업무 원장이다. 캘린더 등록이 계약 변경이나 연락 완료를 뜻하지 않는다.
- 네이버에서 수동 변경한 일정이 계약 DB에 자동 반영된다고 표현하지 않는다.
- 네이버의 알림 설정·권한에 따라 달라지는 알림 전달을 보장하지 않는다.
- 종일 일정·미리 알림·기존 일정 수정은 실제 API 동작 확인 후 지원 범위를 정한다. 검증 전 임의 시간을 부여하지 않는다.
- 일괄 자동 등록과 양방향 동기화, 별도 전체 캘린더 UI는 MVP 제외다. 캘린더 API 자체는 제외하지 않는다.

### 6.3 확인한 공식 API 범위와 미확인 사항

2026-09-16 공식 문서 확인:

- 네이버 로그인은 OAuth 기반 인증과 토큰 처리 문서를 제공한다. 로그인 state 검증과 필요한 최소 프로필 수집을 적용한다. [로그인 API 명세](https://developers.naver.com/docs/login/api/api.md)
- 공개 서비스의 로그인 검수·사용 계정 조건을 배포 전에 확인한다. [로그인 개발 가이드](https://developers.naver.com/docs/login/devguide/devguide.md)
- 네이버 캘린더는 로그인 사용자 일정 등록을 안내한다. [캘린더 API 소개](https://developers.naver.com/products/login/calendar/calendar.md)
- 확인한 일정 추가 명세는 `POST https://openapi.naver.com/calendar/createSchedule.json`이며, 응답 설명에 `create, modify`가 표기되어 있다. 기존 일정 수정의 구체 조건은 실제 검증이 필요하다. 전체 조회·삭제·양방향 동기화 지원은 확인되지 않았다. [캘린더 일정 추가 API 명세](https://developers.naver.com/docs/login/calendar-api/calendar-api.md)

일반 네이버 캘린더와 NAVER WORKS Calendar는 다른 서비스다. WORKS API의 기능을 일반 네이버 계정에서 가능한 것으로 대체하지 않는다. 현재는 문서 확인 단계이며 실제 호출은 하지 않았다.

### 6.4 실패·중복·일정 변경 처리

- 내부 일정 ID, 사용자, 연결 계약, 요청 내용 버전, iCalendar UID, 반환 식별자, 등록 결과를 기록한다. UID는 토큰·전화번호에서 만들지 않는다.
- 같은 작업의 중복 클릭과 동시 요청을 서버에서 차단한다. 성공 확인된 같은 버전은 재등록하지 않는다.
- 타임아웃은 ‘실패’가 아니라 등록 여부 불명일 수 있다. 자동으로 재전송하지 않고 ‘반영 여부 확인 필요’로 안내한다. 같은 UID 재요청의 중복 방지는 실제 검증 후에만 신뢰한다.
- 권한 오류는 연동 확인, 인증 만료는 필요한 재인증으로 처리한다. 무한 재시도하지 않는다.
- 계약일 변경 시 기존 등록 일정의 버전 차이를 알린다. 수정 지원이 검증되면 사용자 확인 후 갱신한다. 미지원이면 네이버에서 기존 일정 확인·수정을 안내하며 새 일정 자동 중복 생성은 하지 않는다.
- 외부 일정의 삭제가 불가능하거나 미확인이라면 웹앱 삭제로 네이버 일정도 삭제됐다고 알리지 않는다.
- 캘린더 오류가 상담·계약 저장을 롤백하거나 기본 조회를 중단시키지 않는다.
- 캘린더 연동 사용 중지와 네이버 로그인 연결 해제를 같은 작업으로 취급하지 않는다.

## 7. AI·RAG 설계 원칙

- 정형 질문: 사용자 인증 → 주요/기타·단지·날짜·유형 등 조건 추출 → 스키마 검증 → 권한 제한 DB 조회.
- 비정형 질문: 허가된 후보의 상담·특이사항 keyword/FTS 검색 → 짧은 근거 → 필요 시 요약.
- 검색·요약은 ‘협의’와 ‘허용’, ‘연락 시도’와 ‘처리 완료’, 예상과 확정을 구분한다.
- 의미 검색은 keyword/FTS baseline 대비 실제 질문 성과가 개선될 때 추가한다. 기준·지연·비용을 실험 전에 정한다.
- 단순 DB 필터나 LLM 조건 추출만 구현했다면 RAG가 완성됐다고 설명하지 않는다.
- 고정된 다단계 처리만으로 Agentic RAG라고 부르지 않는다. 반복된 재검색 실패 패턴과 개선 근거가 있을 때 제한된 루프를 추가한다.
- 초기 재검색은 최대 한 번으로 제한하고, 새 근거 없음·시간/비용 상한·충분한 근거 확보 시 종료한다. 수치는 구현 스파이크로 확정한다.
- 현재 주요/기타 분류 및 매물·고객 관계는 SQL로 처리한다. GraphRAG·Graph DB의 필요는 확인되지 않았다.
- 개인화는 명시적 화면 선호·단지 별칭·승인된 필드 매핑 정도부터 검증한다. 사용자 Wiki로 계약 DB를 대체하지 않는다.
- 문서·메모 안의 지시문은 데이터다. 권한과 외부 작업을 부여하지 않는다.

## 8. 개인정보·운영 요구

1. 로그인 사용자 권한을 서버에서 모든 자료와 외부 캘린더 작업에 적용한다. 주요/기타 분류는 보안 장치가 아니다.
2. 네이버 비밀번호를 수집하지 않는다. 로그인 식별은 제공된 고유 식별자와 내부 사용자 ID로 연결하며 이름·이메일만으로 자동 계정 병합하지 않는다.
3. state 검증, 허용된 callback, HTTPS, 보호된 세션을 적용한다. Client Secret은 서버에서만 관리하고 access/refresh token·인증 코드를 URL 분석 로그·LLM 요청·데모에 노출하지 않는다. 장기 토큰 저장이 필요하면 암호화·접근 제한·폐기 정책을 적용한다.
4. 파일 형식·크기·행 수 제한, 손상/암호 파일 처리, 매크로 실행 금지, 실패 상태와 수동 확인 경로를 제공한다. 운영 상한값은 스파이크로 결정한다.
5. 고객 연락처·상담 원문을 외부 API에 기본 전송하지 않는다. Embedding을 익명화로 취급하지 않는다.
6. 원본 파일·추출값·상담 검색 인덱스·캐시의 보관/삭제 범위를 정한다. 가져오기 확인을 위한 원본 보관 기간과 법정 계약 자료 보관을 구분한다. 무기한 보관하지 않는다.
7. 원본 Excel·전체 연락처·상담 원문·prompt·토큰은 일반 로그에 남기지 않는다. 작업 ID·오류 유형·건수·지연·비용 중심으로 관측한다.
8. 외부 LLM·네이버로 전송하는 정보의 처리 목적·약관·보관·위탁/국외이전 해당 여부를 실제 구성에 맞게 확인한다. 실제 고객 데이터 사용 전 법률·보안 검토가 필요하며 이 문서만으로 준수를 보장하지 않는다.
9. 월 10만 원 예산 내 일별 AI·파일 처리 상한을 설정한다. AI 또는 네이버 장애 시 DB 조회·수동 수정·상담 저장은 유지한다. 가격과 외부 호출 한도는 배포 전 재확인한다.
10. 지속 저장과 최소 백업·복원 검증을 제공한다. 대규모 조직 권한·복잡한 인프라는 선행 요구하지 않는다.

### 먼저 확인할 스파이크

1. 비식별 Excel 샘플의 중요 필드 추출과 3개월 경계 조회.
2. 네이버 애플리케이션 등록·로그인·API 권한·검수 조건, 실제 일정 한 건 등록 및 반환 식별자 확인.
3. 기존 UID 일정 변경·중복 요청·종일/알림 지원 확인. 문서 응답의 modify 표기만으로 자동 동기화를 약속하지 않는다.
4. 주요 관리 아파트 지정과 기타 분류의 실제 사용 방식.
5. 10~20개 대표 질문으로 DB 조회와 상담 검색 baseline 분리.

| 기간 | 목표 | 검증 기준 |
|---|---|---|
| 1주 | 사용자 흐름 검증, 로그인/캘린더 스파이크, 데이터 모델, 한 양식 등록, 분류, 만기 홈 | 중요 필드·날짜·사용자 권한이 올바르고 외부 연동 가능/제약이 기록된다. |
| 2주 | 고객·상담 지속 저장, 계약 갱신, 조건 검색·읽기 전용 챗봇, 확인 후 캘린더 등록 | 재접속 유지와 핵심 업무 완주, 외부 실패 시 기본 업무 유지가 동작한다. |
| 3주 | 등록 실패/충돌 방어, 모바일 사용성, 배포·평가·시연 | 실제 과제 결과와 실패 사례 공개, 로그인 검수와 API 지원 상태를 정확히 표시한다. |
| 4~5주 | 실제 필요한 양식 확대, 재업로드 충돌 UX, 상담 검색 비교 | 보류 양식과 질문으로 이전 대비 품질·수정 부담을 측정한다. |
| 6~8주 | 검증된 의미 검색·제한 재검색, 확인된 일정 수정, 복원·비용·지연 보강 | baseline/ablation·사용자 행동에 따른 추가 또는 제외 이유를 기록한다. |

3주 완료는 외부 검수·실제 양식 복잡도에 따라 불확실하다. 승인 대기 중 제한 계정 테스트를 공개 사용자 로그인 완료라고 표현하지 않는다. 필수 캘린더가 미연결이면 미완료로 표시하고 축소 범위나 일정을 협의한다.

축소 시 복잡한 양식, 이미지 전면 해석, 자동 개인화, Agent, 계약 파일 추출, 양방향 동기화부터 제외한다. 네이버 로그인·최소 캘린더 등록·주요/기타 분류·만기 업무·지속 저장·필수 챗봇은 사용자 요구이므로 임의로 제외하지 않는다.

## 11. 데모 상태와 다음 확인사항

기존 `매물온_화면데모_v0.3.html` 및 `work/demo/property-management-demo.html`은 이번 정정 전 목업이다. 이번 작업은 명세와 공유 기준의 수정이며 화면·코드 구현 변경은 아니다.

기존 데모는 허구 매물·마스킹 연락처, 로컬 샘플 조회·상담·등록 흐름만 제공한다. 실제 Excel·LLM/RAG·인증·DB 지속 저장·네이버 캘린더는 미연결이며 재실행 시 초기화된다. 주요/기타와 네이버 연동이 화면에 구현되어 있다고 설명하지 않는다.

다음 확인사항:

- 주요 관리 아파트의 수와 지정/분류 방식, 기타에 포함할 실제 매물 예시
- 네이버에 담고 싶은 일정: 만기, 후속 연락, 두 가지 중 무엇인지
- 일정 수동 등록/등록 후 갱신/알림에 대한 실제 기대
- 공동 계정·다른 로그인 사용자와 공유 필요 여부
- 등록 이후 Excel과 웹앱의 역할, 연락 상태의 최소 표현
- 네이버 등록·검수·API 실제 지원 범위와 성공/실패 조건

이 문서는 로컬 요구사항이다. ChatGPT 프로젝트 메모리 동기화나 외부 업로드를 뜻하지 않는다.
